# Evaluation Framework Architecture

# 01. Purpose

Define a reproducible, model-agnostic framework for measuring and comparing *out-of-sample* forecasts generated by the exuting backtesting runner. Evaluation consumes forecast records; it does not refit models, create folds, or alter forecast outputs. its job is to turn prediction-actual pairs into interpretable error metrics, diagnostics, and fair comparisons.

---

# 02. Relationship to the existing platform

established and tested foundation: ForecastDataset, BaseForecaster, ForecastResult, SeasonalNaiveForecaster, chronological BacktestConfig/BacktestFold/generate_folds, and backtesting execution runner. 

- 07_backtesting_design.md owns temporal splitting, model fitting, prediction, and the long-format out-of-sample record contract.

- 08_evaluation_framework.md owns metric definition, input validation, aggregation, diagnostics, and comparison policies. 

- 09_pipeline_architecture.md will orchestrate evaluation within end-to-end workflows; 12_experiment_tracking.md will govern persisitence and governance.

- Existing dataset, model, and backtest APIs remain unchanged unless a verified integration issue requires and explicit decisions.

---

# 03. Design Principles 

- *Out-of-sample only*: score predictions emitted by the backtesting runner, never fitted values.

- *Traceability*: retain run, model, series, fold, origin, target time, and horizon for every scored point. 

- *Fairness*: compare models on identical evaluation keys and document missing coverage.

- *Explicit semantics*: metric formulas, units, direction, undefined cases, and aggregation rules must be documented.

- *No silent cleaning*: missing, infinite, duplicated, or misaligned records fail validation or follow and explicitly chosen policy.

- *Separate computation from interpretation*: calculate metrics first, then summarize, rank, visualize, or test significance.

- *Incremental scope*: single-series deterministic point forecast first; probabilistic, hierarchical, and decision metrics later.

Validate required columns, compatible dtypes, nonempty input, uniqueness of (*run_id, model_id, series_id, fold_id, forecast_orifin, targte_timestamp, horizon*), and *temporal ordering*. The horizon must agree with the origin/target frequency when that frequency is supplied. The inital behavior must not infer calendar frequency from arbitrary row order.

# 05. Evaluation levels and grouping 

| Level | Default grouping | Purpose |
|---|---|---|
| Overall | run_id, model_id | Single headline metric per model/run |
| By horizon | run_id, model_id, horizon | Error growth with lead time |
| By fold | run_id, model_id, fold_id | Performance across historical origins |
| By period | run_id, model_id, defined time bucket | Drift and seasonality diagnostocs |
| By series (future) | run_id, model_id, series_id | Panel and portfolio comparisons | 

All aggregate outputs include n_observations and coverage metadata. Do not treat repeated observations from overlapping backtest folds as independent evidence when reporting uncertainty or statistical tests.

# 06. Point forecast metrics

Let $e_i = y_{\text{true},i} - y_{\text{pred},i}$ and $n$ be the number of valid scored records. Lower is better for error magnitudes; bias is ideally near zero.

| Metric | Definition | Interpretation/caution |
|---|---|---|
| **MAE** | $\frac{1}{n} \sum \vert e_i \vert $ | Same units as target; robust relative to squared-error metrics |
| **MSE** | $\frac{1}{n} \sum e_i^2$ | Squared target units; emphasizes large errors |
| **RMSE** | $\sqrt{\text{MSE}}$ | Target units; emphasizes large misses |
| **Bias/ME** | $\frac{1}{n} \sum (y_{\text{pred},i} - y_{\text{true},i})$ | Positive = systematic overprediction |
| **WAPE** | $\left( \frac{\sum \vert e_i \vert}{\sum \vert y_{\text{true},i} \vert} \right) \times 100$ | Undefined when $\sum \vert y_{\text{true},i} \vert = 0$; dominated by high-volume observations |
| **sMAPE** | $\frac{100}{n} \sum \frac{2\vert e_i \vert}{\vert y_{\text{true},i} \vert + \vert y_{\text{pred},i} \vert}$ | Undefined for $\frac{0}{0}$ without an explicit policy; can behave poorly near zero |
| **MASE** | $\frac{\text{MAE}}{q_f}$ | Requires strictly in-sample denominator per fold; not computable from $(y_{\text{true}}, y_{\text{pred}})$ alone |

The initial implementation should prioritize MAE, RMSE, MSE, and signed bias. WAPE and sMAPE are optional next-step metrics with explicit zero handling. MASE requires a training-history-derived scale recorded per fold or provided via a controlled auxiliary input; do not compute its denominator using evaluation-period clusters.

---

# 07. MASE and scale-dependent denominators

For a training sequence $y_1, ... , y_T$ and seasonality $m$, the *in-sample* seasonal-naive scale is:

$$
q= \frac{1}{T-m} \sum_{t=m+1}^T |y_t−y_{t−m}|
$$ 

For fold $f$:

$$
\text{MASE}_f = \frac{\text{mean}(|\text{forecast errors in} f|)}{q_f}
$$

Require:
* $T > m$
* $q_f > 0$
otherwise report undefined with a reason, not an invented zero. Since expanding and sliding window have different training histories, scales can vary by fold. Record the scale source, $m$, and calculation window.        

---

# 08. Aggregation Policy

Distinguish micro and macro aggregation. Micro MAE pools all eligible forecast rows: $\frac{|e|}{N}$. Macro MAE avergaes fold - or series-level MAEs, Optionally with explicit weights. These need not agree when group sizes differ. For RMSE, pool squared errors before taking the square root; do not average RMSE values and label the result pooled RMSE. 

Default initial behaviour: calculate row-level errors, then pooled metrics over a selected group with $n$ and distinct fold count. Publish optional per-fold and per-horizon tables. DO not average per-row WAPE or per-row MASE denominators indiscriminately. 

---

# 09. Comparison Contract 

A model comparison must use a matched cohort: identical(series_id, forecast_origin, target_timestamp, horizon) evaluation keys, with run identity handled explicitly. Report candidate row count, matched row count, unmatched keys and coverage percentage. 

Reject comparisons of incompatible targets, frequency, or horizon definitions. Ranking is permitted only after cohort alignment and explicit metric direction. 

Recommended comparisons: MAE/RMSE difference, 

$$
\text{relative improvement} = \frac{\text{baseline_error - candidiate_error}}{\text{baseline_error}} \times 100 [\text{undefined if baseline_error}= 0 ].
$$

bias comparison, and horzon-sepcific profiles. Preserve baseline model identification in outputs.

---

# 10. Statistical inference (planned, not initial implementation)

Forecast origins from rolling-origin evaluation are often correlated, especially when horizons overlap. Do not apply ordinary independent-observation t-tests to every score row. Future options include *paire loss-differential analysis*, *Diebold-Mariano-type tests* with appropriate *autocorrelation treatment*, or *bloc/boots

---

# 11. Diagnostics and visualizations

- Actual versus predicted by target timestamp, with fold/origin filtering.

- Absolute and signed error distributions; quantiles and extreme-error cases.

- MAE/RMSE/bias by horizon and by fold.

- Rolling or calendar-bucket errors, where sufficient observations exist.

- Coverage matrix by model and horizon, highlighting missing or invalid records.

- Matched-cohort model comparison chart; show sample sizes and uncertainty only when statistically justified.

# 12. Proposed Output Contracts

Do not introduce an alternative forecast result schema. The evaluator should return pandas DatFrames or a small typed result wrapper whose tables have stable columns. 

| Output | Mimimum fields |
|---|---|
| Metric summary | run_id, model_id, group_keys, metric, value, n_observations, n_folds |
| Scored observations | All original forecast keys plus error, absolute_error, squared_error |
| Comparison summary | baseline_model_id, candidate_model_id, metric, baseline_value, candidate_value, absolute_difference, relative_improvement_pct, matched_n |
| Validation report (optional) | rule, severity, affected_count, sample_keys |

Maintain metric names, denominator policies, group keys, and implementation version in metadata. Undefined metrics should use NaN/nullable values accompanied by a documented reason, never silently converted to zero.

# 14. Validation and Failure Policy

- Fail fast for missing required fields, duplicate forecast keys, invalid numeric values, impossible timestamps, or unsupported metric names.

- Validate that successful predictions contain the expected evaluated horizons and timestamps.

- Explicitly define zero-denominator handling for WAPE/sMAPE and undefined training scale for MASE.

- Reject empty matched cohorts for model comparisons; report coverage shortfalls rather than filling missing predictions.

- Do not mutate the caller’s DataFrame. Preserve original rows and key columns.

- Use clear exception messages with metric, run/model, and affected fold context; avoid exposing full sensitive records in logs.

---
 
# 15. Testing Strategy

*Unit tests*: hand-calculated MAE/MSE/RMSE/bias; zero and negative targets; perfect forecasts; singleton data; invalid types; NaN/Inf; duplicate keys; unsupported metric; grouping and counts; nonmutation; deterministic ordering.

*Integration tests*: consume actual runner output from SeasonalNaiveForecaster; verify exact golden scores by fold and horizon; compare two model outputs on matching keys; verify gap-aware horizons; confirm the complete existing suite still passes.

*Property tests*: MAE/MSE/RMSE nonnegative; RMSE ≥ MAE on the same finite cohort; all-zero residuals imply zero MAE/RMSE/bias; reordering rows does not change aggregate results; adding identical forecast rows with duplicate keys is rejected.
