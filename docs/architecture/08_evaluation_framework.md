# Evaluation Framework Architecture

# 01. Purpose

Define a reproducible, model-agnostic framework for measuring and comparing *out-of-sample* forecasts generated by the exuting backtesting runner. Evaluation consumes forecast records; it does not refit models, create folds, or alter forecast outputs. its job is to turn prediction-actual pairs into interpretable error metrics, diagnostics, and fair comparisons.

---

# 02. Relationship to the existing platform

established and tested foundation: ForecastDataset, BaseForecaster, ForecastResult, SeasonalNaiveForecaster, chronological BacktestConfig/BacktestFold/generate_folds, and backtesting execution runner. 

- 07_backtesting_design.md owns temporal splitting, model fitting, prediction, and the long-format out-of-sample record contract.

- 08_evaluation_framework.md owns metric definition, input validation, aggregation, diagnostics, and comparison policies. 

- 09_pipeline_architecture.md will orchestrate evaluation within end-to-end workflows; 12_experiment_tracking.md will govern persisitence and governance.

- Existing dataset, model, and backtest APIs remain unchanged unless a verified integration issue requires and explicit decisions.

---

# 03. Design Principles 

- *Out-of-sample only*: score predictions emitted by the backtesting runner, never fitted values.

- *Traceability*: retain run, model, series, fold, origin, target time, and horizon for every scored point. 

- *Fairness*: compare models on identical evaluation keys and document missing coverage.

- *Explicit semantics*: metric formulas, units, direction, undefined cases, and aggregation rules must be documented.

- *No silent cleaning*: missing, infinite, duplicated, or misaligned records fail validation or follow and explicitly chosen policy.

- *Separate computation from interpretation*: calculate metrics first, then summarize, rank, visualize, or test significance.

- *Incremental scope*: single-series deterministic point forecast first; probabilistic, hierarchical, and decision metrics later.

---

# 04. Input Contract

The evaluator consumes the runner's long-format backtest results, preferbaly as a pandas DataFrame. The initial point-forecast contract is:

| Field | Meaning/rule |
|---|---|
| run_id | Nonemepty run identifier |
| model_id | Stable model identifier |
| series_id | Nullable for initial single-series runs |
| fold_id | Positive fold identifier |
| forecast_origin | Historical timestamp at forecast issuance |
| target_timestamp | Timestamp of evaluated actual |
| horizon | Positive integer periods ahead of origin | 
| y_true | Finite observed target (numeric) |
| y_pred | Finite point forecast (numeric) |
| fit_status, predict_status | Successful status required for scored records; explicit failure policy later |

Validate required columns, compatible dtypes, nonempty input, uniqueness of (*run_id, model_id, series_id, fold_id, forecast_orifin, targte_timestamp, horizon*), and *temporal ordering*. The horizon must agree with the origin/target frequency when that frequency is supplied. The inital behavior must not infer calendar frequency from arbitrary row order.   

---

# 05. Evaluation levels and grouping 

| Level | Default grouping | Purpose |
|---|---|---|
| Overall | run_id, model_id | Single headline metric per model/run |
| By horizon | run_id, model_id, horizon | Error growth with lead time |
| By fold | run_id, model_id, fold_id | Performance across historical origins |
| By period | run_id, model_id, defined time bucket | Drift and seasonality diagnostocs |
| By series (future) | run_id, model_id, series_id | Panel and portfolio comparisons | 

All aggregate outputs include n_observations and coverage metadata. Do not treat repeated observations from overlapping backtest folds as independent evidence when reporting uncertainty or statistical tests.

---

# 06. Point forecast metrics

Let e_i = y_true,i - y_pred,i and n be the number of valid scored records. Lower is better for error magnitudes; bias is ideally near zero.

| Metric | Definition | Intepretation/caution |
|---|---|---|
| MAE | (1/n)(Σ \|e_i\) | Same units as target; robust relative to squared-error metrics |
| MSE | (1/n) (Σ e_i² ) | Squared target units; emphasizes large errors |
| RMSE | sqrt(MSE) | Target units; emphasizes large misses |
| Bias/ME |  (1/n) Σ (y_pred,i − y_true,i) | Positive = systematic overprediction |
| WAPE | ((Σ \|e_i\|) / (Σ \|y_true,i\|)) × 100 | Undefined when Σ\|actual\| = 0; dominated by high-volume observations |
| sMAPE | (100/n) Σ [2\|e_i\|/(\|y_true,i\|+\|y_pred,i\|)] | Undefined for 0/0 without an explicit policy; can behave poorly near zero |
| MASE | MAE/(training seasonal-naive scale) | Requires strictly in-sample denominator per fold; not computable from (y_true/y_pred) alone |

The initial implementation should prioritize MAE, RMSE, MSE and signed bias. WAPE and sMAPE are optional next-step metrics with explicit zero handling. MASE requires a training-histor-derived scale recorded per fold or provided via a controlled auxiliary input; do not compute its denominator using evaluation-period clusters.


---

# 07. MASE and scale-dependent denominators

For a training sequence $y_1, ... , y_T$ and seasonality $m$, the *in-sample* seasonal-naive scale is:
                     q=(1/(T-m))Σ[t=m+1..T] |y_t−y_(t−m)|
For fold $f$:
             $$MASE_f = mean(|forecast errors in f|)/q_f$$
Require:
* $T > m$
* $q_f > 0$
otherwise report undefined with a reason, not an invented zero. Since expanding and sliding window have different training histories, scales can vary by fold. Record the scale source, $m$, and calculation window.
